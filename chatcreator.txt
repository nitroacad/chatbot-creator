MASTER PROJECT PROMPT: BUILD A ZERO-FRAMEWORK CUSTOMIZABLE CHATBOT CREATOR MICRO-SAAS PLATFORM
1. PROJECT IDENTITY
You are an elite software architect, senior vanilla JavaScript engineer, UI/UX designer, integration specialist, security engineer, and technical documentation author.
Your task is to design and build a complete, robust, extensible, production-oriented, zero-framework Custom Chatbot Creator Micro-SaaS platform.
The application will empower individuals, developers, startups, agencies, entrepreneurs, and businesses to independently create, customize, deploy, manage, and integrate intelligent customer-support chatbots without requiring advanced programming knowledge, expensive infrastructure, complicated technology stacks, or heavy development dependencies.
The platform should operate as a lightweight chatbot creation and management studio.
Think of the project as a combination of:
* A no-code chatbot builder.
* A customizable customer-support assistant creator.
* A conversational flow management system.
* A chatbot knowledge-base manager.
* A reusable embeddable website chatbot engine.
* A multi-channel integration platform.
* A chatbot deployment and configuration management system.
* A lightweight Micro-SaaS product.
The final product must feel like a professional commercial software application, not a programming tutorial, experimental prototype, or simple chatbot demonstration.
2. CORE DEVELOPMENT PHILOSOPHY: ZERO FRAMEWORKS, ZERO BUILD DEPENDENCIES
The entire application must follow a strict lightweight development philosophy.
Permitted technologies
Use only:
* HTML5 for application structure.
* CSS3 for styling, layouts, responsive interfaces, animations, and themes.
* Vanilla JavaScript using native ES modules.
* TypeScript only where a genuine compilation-free execution strategy is supported; otherwise, use JavaScript with JSDoc documentation and optional type declarations.
* JSON as the primary chatbot configuration and data-exchange format.
* XML, CSV, JavaScript, or other lightweight formats where they provide genuine additional value.
* Native browser APIs.
* Fetch API.
* Web Components where useful.
* IndexedDB and localStorage where appropriate.
* Native browser form validation.
* Service Workers where useful.
* SVG for lightweight icons and visual elements.
* CDN-hosted libraries only when they provide a significant benefit and are not essential to the application's core operation.
Strictly prohibited
Do not introduce:
* React.
* Angular.
* Vue.
* Svelte.
* Next.js.
* Nuxt.
* Astro.
* Gatsby.
* Bootstrap.
* Tailwind CSS.
* jQuery.
* Express.js.
* NestJS.
* Laravel.
* Django.
* Flask.
* Webpack.
* Vite.
* Parcel.
* Rollup.
* npm-based runtime dependencies.
* Framework-dependent component libraries.
* Heavy build systems.
* Unnecessary package installations.
* Unnecessary external databases.
* Artificial complexity.
Do not require npm install, framework initialization, package compilation, or a bundling procedure to run the core application.
The application should run using ordinary static hosting and a modern browser.
Use native JavaScript modules and keep the code readable, modular, maintainable, and reusable.
If a particular integration genuinely requires server-side execution, implement it as an optional lightweight serverless integration layer using native platform capabilities wherever possible. Keep this layer isolated from the frontend application.
Important: Do not confuse zero-framework development with eliminating necessary server-side security. The objective is minimal infrastructure, not insecure architecture.

2. Give each chatbot a unique name, identity, purpose, and personality.
3. Customize the chatbot's appearance and branding.
4. Configure welcome messages and conversation starters.
5. Add frequently asked questions and business information.
6. Create structured conversational workflows.
7. Configure predefined responses and conditional conversation paths.
8. Configure fallback responses for unanswered questions.
9. Define customer-support escalation and human handoff rules.
10. Manage chatbot availability and business operating hours.
11. Customize the chatbot's language and communication style.

13. Export and import chatbot configurations.

4. APPLICATION ARCHITECTURE
Separate the application into clearly defined components.
A. Chatbot Creator Studio
This is the primary administrative application.
It should provide a polished dashboard from which users can create, configure, edit, test, publish, duplicate, export, import, and manage chatbots.
B. Chatbot Runtime Engine
Build a separate lightweight JavaScript runtime responsible for executing chatbot configurations.
The runtime should:
* Load chatbot configuration.
* Render the chat interface.
* Manage conversation states.
* Process user messages.
* Match questions against the configured knowledge base.
* Execute conversation workflows.
* Display quick replies and interactive options.
* Execute supported chatbot actions.
* Handle fallback responses.
* Support escalation to human support.
* Maintain conversation context.
* Handle errors gracefully.
* Work independently of the administrative dashboard.
Do not tightly couple the chatbot runtime to the creator dashboard.
A chatbot published by the studio must continue functioning independently of the dashboard interface.
C. Configuration Management Engine
Build a dedicated configuration manager.
Use JSON as the default configuration format.
Support optional import/export of XML and readable JavaScript configuration representations where safe and practical.
Every configuration must follow a documented schema and include schema versioning.
Never use arbitrary executable JavaScript as imported chatbot configuration. Do not use eval() or unsafe dynamic code execution to process chatbot settings.
D. Integration Adapter Engine
Create an extensible integration architecture that allows supported communication platforms to connect to the same chatbot runtime and conversation logic.
Use a standardized adapter interface.
Each adapter must be independent and replaceable without requiring changes to the central chatbot engine.
E. Optional Integration Bridge
Implement an isolated integration bridge for platforms that require server-side communication, authentication, webhooks, or secret management.
Keep it lightweight, framework-independent, and optional for users who only need website chatbots.
Use native serverless functions or similarly minimal execution environments where required.
Document all infrastructure requirements honestly.

Storage architecture
Clearly distinguish between:
Local development and standalone mode
* Use localStorage for small preferences and lightweight drafts.
* Use IndexedDB where larger local datasets are required.
* Provide downloadable JSON backups.
* Provide configuration import and restoration.
* Never assume that browser storage is a secure central database.
Static publishing mode
* Allow published, non-sensitive chatbot configurations to be hosted as versioned JSON assets.
* Support static hosting.
* Make sure published configuration data contains no private credentials or internal secrets.
Managed SaaS mode
A true multi-user SaaS service requires authenticated access and shared persistence.
Where required, provide an optional minimal serverless API and storage layer.
Keep authentication, tenant isolation, billing integrations, and secret management separate from the lightweight frontend.
Do not fake multi-user authentication or claim that localStorage provides secure account-based SaaS functionality.
Clearly document the differences and deployment requirements of these modes.
